# Multi-Tenancy Strategy

## Initial choice

Use one PostgreSQL database with shared tables and explicit `tenant_id` columns on hospital-owned records. A hospital is the tenant root and `hospitals.id` is its tenant UUID; do not add a second tenant identifier. This keeps the initial modular monolith operationally simple while supporting multiple hospitals. It increases the impact of a missing tenant predicate, so isolation must be enforced at every layer.

Schema-per-tenant and database-per-tenant remain future options if customer contracts, residency, backup/restore boundaries, scale, or risk requirements justify their additional provisioning and migration burden. This architecture is not a compliance claim.

## Identity and tenant relationships

- `users`, patient identity, and doctor identity are platform-level identities.
- A `membership` links a staff `user` to a tenant and optionally a branch; `membership_roles` assigns scoped roles. A doctor can be affiliated with multiple hospital tenants through `doctor_affiliations`.
- `patient_registrations` links a global patient identity to a hospital. Appointments and future clinical/operational records are tenant-scoped and reference the patient through that relationship.
- Hospital, branch, schedule, doctor affiliation, appointment, and audit records carry explicit tenant context as applicable.
- Tenant UUIDs are generated by the platform and immutable. Never accept a tenant ID in a request payload as proof of authority.

## Request isolation

1. Authentication resolves the actor and current active memberships.
2. A requested organization/branch context is checked against those memberships; patient requests use the actor's patient identity and explicit registration/relationship.
3. Authorization policies require tenant context. Every module service and repository method that reads tenant data takes that context explicitly; avoid generic unscoped lookups.
4. Writes stamp tenant IDs from trusted context. Queries filter by tenant, including lookups by public UUID.
5. Use composite uniqueness and composite foreign keys such as `(tenant_id, branch_id)` to prevent cross-tenant parentage. Return consistent not-found behavior when a cross-tenant record must be concealed.
6. Booking constraints, idempotency records, audit queries, caches, exports, and future object keys are partitioned by tenant.

## Database defense

Include `tenant_id` directly on tenant-owned rows, even where a parent path could infer it. Add `UNIQUE (tenant_id, id)` where needed as a target for composite foreign keys. Index tenant columns with common access patterns. PostgreSQL row-level security may later provide defense in depth, but only after connection pooling and transaction-local tenant context are designed and verified; it does not replace application policy.

## Privileged and cross-tenant access

Hospital administrators are limited to assigned tenants. `SUPER_ADMIN` is platform-scoped and normally operates on tenant metadata. Exceptional patient/clinical support access, when such data exists, must be explicitly granted, reasoned, time-limited, narrow, audited, and reviewed; there is no silent impersonation path. A shared patient identity alone does not authorize cross-hospital record sharing. Any such sharing requires separately defined consent or legal basis, scope, purpose, expiry/revocation, and access audit.

## Validation before production

Before using real patient data, establish automated cross-tenant isolation checks, migration review, scoped query conventions, access review, backup/restore boundaries, monitoring, and a jurisdiction-specific privacy/security/retention assessment. Do not claim compliance based on this document.
