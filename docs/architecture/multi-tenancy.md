# Multi-Tenancy Strategy

## Recommendation

Use **one PostgreSQL database with shared tables and a non-null `tenant_id` on tenant-owned records** for the initial portfolio release. This is the least operationally complex option for one modular monolith and supports cross-hospital patient identity through explicit patient/tenant relationships. It scales sufficiently for an initial product if isolation is consistently enforced. Schema-per-tenant and database-per-tenant add migration, connection, backup and provisioning overhead before there is evidence they are needed.

| Option | Benefits | Costs | Decision |
|---|---|---|---|
| Shared DB + `tenant_id` | Simple deployments/migrations; efficient pooled resources; easy reporting; practical for portfolio MVP | Application query isolation must be rigorous; noisy-neighbor and blast-radius concerns | **Choose initially** |
| Schema per hospital | Stronger namespace separation; shared DB engine | Many-schema migrations, connection/search-path hazards, harder cross-tenant operations | Revisit for a customer isolation requirement |
| Database per hospital | Strongest infrastructure boundary and independent backup/restore | High cost and provisioning/migration/monitoring burden; complicates central operations | Consider for contractual/regulatory/customer scale needs |

This recommendation is an architecture choice, not a compliance claim. PostgreSQL row-level security may be evaluated as defense in depth after the connection-pooling and session-context design is proven; it must not be enabled as an incomplete substitute for application authorization.

## Tenant identification and data model

- Hospitals are tenant roots; branches, departments, staff assignments and hospital workflows belong to a hospital tenant.
- Tenant IDs are opaque UUIDs generated by the platform and immutable. Never derive them from user-supplied names or trust a raw request parameter.
- Staff obtain tenant context from a verified active membership. A requested hospital/branch selector is only a request to switch among memberships the actor already holds.
- Patients may interact with several hospitals. Their identity is platform-level; clinical/operational resources are tenant-scoped and connected through explicit patient-to-tenant relationships. Do not put one `tenant_id` on a globally shared patient identity if that prevents multi-hospital care.
- Every tenant-owned table carries `tenant_id` directly or has a rigorously enforced parent path. Prefer explicit tenant columns for queryability and composite foreign keys for consistency.

## Isolation controls

1. Authentication resolves actor and active memberships.
2. Authorization selects an allowed tenant context from those memberships or from a verified patient relationship.
3. Service/repository methods require tenant context; avoid unscoped generic lookup helpers.
4. Queries filter by `tenant_id`; writes stamp it from trusted context, never the payload.
5. Composite uniqueness and foreign-key constraints include tenant keys where applicable (for example `(tenant_id, id)` references).
6. Never reveal cross-tenant record existence through different error behavior. Add adversarial cross-tenant access tests during implementation.
7. Background jobs carry tenant ID and actor/purpose metadata; workers revalidate scope rather than trusting arbitrary serialized object IDs.
8. Cache keys, object keys, exports, search indexes and logs include tenant-safe partitioning and must not be shared accidentally.

## Administrative and cross-tenant access

Hospital admins are restricted to their hospital. Super-admin platform tasks should use metadata by default. Clinical access for support is exceptional, time-bound, reasoned and audited (break-glass), with alerting/review. No endpoint should accept `tenant_id` as authority. Cross-tenant patient record sharing requires explicit patient consent or another verified legal basis, a purpose, narrow scope, expiry/revocation and access logging; it is not implied by a shared patient account.

## Risks and future migration

Shared tenancy creates a large impact if a query omits its tenant predicate. Before production, use automated isolation tests, query conventions, code review and potentially database RLS as defense in depth. If customer isolation, data residency, restore boundaries or scale demand separate databases, design a tenant routing abstraction at the persistence boundary and migrate tenant groups deliberately.
